# Notify triggers on pi-native lifecycle events

We decided (2026-08, pi 0.84.4) to re-base the notify package's two trigger paths on pi's own lifecycle events instead of internal plumbing: the "task complete" path keys on `agent_settled` (replacing `agent_end`), and the "question needs your answer" path keys on the `ui_prompt_start` extension event (replacing the bus `ASK_REQUEST` listener). Both config keys (`notifyOnAgentEnd`, `notifyOnQuestion`) keep their names and locations; only the wiring under them changes. Concomitantly, notify's `@earendil-works/pi-coding-agent` peer floor moves from `>=0.1.0` to `>=0.84.4` — the only package whose *behavior* depends on a pi event that does not fire on older versions — while the dev type-check floor of all twelve packages moves to `^0.84.4`.

The two switches fix two different gaps. `agent_end` can fire while the run is not actually finished — pi may still perform queued continuations or mid-run compaction behind it (the in-run compaction pass in 0.84.4, #6879, made this tighter). `agent_settled` fires only when *no* automatic retry, compaction, or queued continuation will run after, which is exactly what "Task complete — waiting for input" should promise. It has existed since pi 0.80.4, so it is typed under our prior floor at zero new risk. `ui_prompt_start` fires in the parent process around every blocking `ctx.ui` prompt, of any kind: ask (direct and subagent-relayed — the relay calls `ctx.ui` in the parent, so both paths converge), the sudo password prompt and its confirm, and the mcp OAuth loader. The old bus listener covered only ask, and only because ask took the trouble to emit a nursery event that **only notify consumed** — the coupling direction was backwards for the one consumer it served.

The rejected alternative was the lenient hybrid: keep the `ASK_REQUEST` listener as a fallback for pre-0.84.4 pi and layer `ui_prompt_start` on top, keeping peer floors at `>=0.1.0` forever. Two paths for one notification, a permanent second wiring to keep understood, and a silently-degraded feature (no question notifications at all below the floor) anyway — the fallback only covers ask, so a 0.84.3 user was never at parity with a 0.84.4 user. We picked the single path plus an honest floor instead.

The bus `ASK_REQUEST` event is **not** retired — it remains ask↔subagent transport (child request framed over the IPC bridge, parent relay listens on it to surface the prompt). Only notify's use of it goes away; ask keeps owning the event's emission.

Consequences:
- Notify no longer imports `@pi-archimedes/core/bus` (it keeps core for `settings-io`).
- No reusing `event.title` in the copy, no kind filter; the notification copy is unchanged ("A question needs your answer"). A `ui_prompt_end` handler cancels the question timer when a prompt closes — needed for prompts that close without terminal input (e.g. the mcp OAuth `done()`), which the earlier "answers pass through terminal input" assumption got wrong; it is scoped so it never wipes a pending "task complete" timer.
- Accepted edge: a user AFK on a `/mcp` panel mid-run gets a question notification — same tolerated trade as `agent_end` already made, defused by the delay and any-key cancel.
- Asymmetric peer floors across the monorepo are deliberate: packages whose new code only needs *types* from pi (`pi-tui` floor, `Theme.fg` cleanup) stay `>=0.1.0` peers because those call sites are runtime-safe on older pi.
