# Plugin gate in each package's own namespace

We decided (2026-08, post-plan-031 review of a live settings file) to change the *config shape* of the plugin gate introduced by [ADR 0011](./0011-plugin-manager.md): the on/off switch for each optional package moves from the standalone `archimedes.plugins` map into that package's **own settings namespace** — `archimedes.<pkg>.enabled`. ADR 0011's architecture stands as-is: the discovery-driven `PLUGINS` manifest in meta, the three enforcement points (registration, settings items, shutdown), the dedicated `/plugins` toggle overlay, session-scoped effect, and core's absolute exemption. Only the shape — and one consequence for plan-030 — changes here.

The semantics are **default-on, meta-owned**: a plugin with manifest `namespace` `NS` is enabled iff `settings[NS].enabled !== false`; meta (via `settings-io` helpers) is the ONLY reader that decides behavior and the ONLY writer, toggled through `/plugins`. Toggling On deletes the key (restoring the default), toggling Off writes `enabled: false` merged into the package's own namespace. The pre-existing `enabled` flags on `notify` and `session-name` are **promoted** rather than deleted: the same key keeps its location, but the packages stop reading it at runtime (their runtime guards and `/archimedes` toggle rows go away) and meta's registration gate becomes its only consumer.

This amends ADR 0011's "considered and rejected: per-package `enabled` flags everywhere." That rejection was aimed at the failure we actually observed — a package reading its own flag at runtime ON TOP of the suite gate, so the feature could be "enabled" in two conflicting spots (`archimedes.notify.enabled: false` while the gate said on). The killed design and this design differ on who consumes the key: once meta is the sole reader and no package code touches `enabled`, "multiple toggles" degenerates to **one toggle per package with one consumer** — the conflict class disappears, and each switch sits next to the settings it governs instead of a parallel roster. What the standalone map gave up: a single-file grep of every on/off state (`archimedes.plugins`). Accepted trade — for this suite the per-package location is the more discoverable one, and `/plugins` remains the single UI surface listing all of them.

Migration is one-shot and idempotent: at meta startup, each legacy `archimedes.plugins.{id}: false` entry is written as `enabled: false` into that plugin's manifest namespace (explicit `true` entries need nothing — they equal the default; unknown ids are dropped), then the `archimedes.plugins` key is removed from settings.json.

Consequences:
- **Plan-030 (sudo) constraint flips.** ADR 0011 said sudo must NOT ship its own `enabled` flag. Under this shape it MUST, like every other package: `archimedes.sudo.enabled`, gated by the same meta mechanism, no sudo-internal runtime guard. Plan-030's "sudo has NO enabled config" cross-note is voided by this ADR.
- New packages ship a manifest entry whose `namespace` is their settings key; the `enabled` key appears in their namespace only when a user toggles them off (or keeps an explicit on) — nothing else.
- The legacy map will no longer exist in settings.json after first run of a build that includes this change.
