# Sudo access: active tool_call veto guard + single-credential in-memory cache

Issue #33 asks for first-class, safety-focused `sudo` support in pi-archimedes: a dedicated `sudo_exec` tool that prompts for a password through a masked interactive UI only, passes it via `sudo -S` stdin, caches it only in memory for the active session, and blocks agents from driving interactive `sudo` through the normal `bash` tool.

We decided (2026-08, design discussion) on:

- **An active guard that actually vetoes `bash` tool calls.** The guard subscribes `pi.on("tool_call")` and, when `toolName === "bash"` and the command contains an interactive `sudo` that can prompt, returns `{ block: true, reason }`. Verified in pi 0.84.3 source (`agent-session.js`, `agent-loop.js`, `extensions/runner.js`; shipped example `examples/extensions/permission-gate.ts`): a `tool_call` handler returning `block: true` produces an immediate error tool result and the tool's `execute()` — and therefore the shell `spawn` — never runs. The earlier design draft proposed consuming the `tool_execution_start` **bus event**; research showed that surface is observational only (its handler has no return value; `runner.js` ignores handler results for it), so it cannot stop execution. The veto lives on the separate `tool_call` event, fired after `tool_execution_start` but before execution.
- **Unconditional block, no user-confirmation bypass.** The block is unconditional: bash→interactive-sudo always fails, with a clear reason telling the model to use `sudo_exec` instead (which itself displays the exact command and a human-readable reason before prompting). pi's shipped `permission-gate.ts` pattern (confirm each risky command interactively) was considered and rejected — issue #33 explicitly says "block direct interactive sudo calls from the normal bash tool," and a bypass on the bash path would defeat the purpose of funneling privileged execution through `sudo_exec`. `sudo -n` / `-l` / `-v` / `-K` / `-k` always pass (they cannot prompt).
- **Single in-memory credential, scoped to the active session.** One credential at a time, stored in a plain module object with an expiry timestamp, never written to disk or the OS keyring (keyring persistence is a future plan). Cleared on `session_shutdown`, on TTL expiry (default 15 min, configurable), on auth failure, and via an explicit `/sudo forget` command. Host/user keying is deferred to the future SSH variant (YAGNI for v1).
- **Password only ever via masked UI and stdin.** The prompt is a masked custom component (`ctx.ui.custom`, ask's picker precedent) rendering `•` per character; the password goes to `sudo -S` over stdin only — never argv, env, logs, or files, and never a `password` parameter in the tool schema. Headless sessions (`ctx.hasUI === false`, e.g. subagent children) are blocked with a clear error rather than prompted (child `sudo_exec` via an IPC socket bridge is deferred).

Security posture: the guard is a pure, exhaustively-tested scanner (`isInteractiveSudoAttempt`) so the "no mixed command bypasses the guard" guarantee is a tested function, not scattered shell handling. The guard and tool live in one package (`packages/sudo`), auto-load in subagent children (extensions are per-process and children load them), and `enabled: false` in config makes both inert.

Considered and rejected:

- **Passive guard (observe only):** cannot deliver the issue's core guarantee (a command still runs); rejected after research showed the active veto surface exists.
- **Override `/bash` by re-registering a same-named tool:** possible (pi allows it, `tool-override.ts`), but replaces the built-in for the whole session and must reproduce `Details` types exactly; the `tool_call` veto is less invasive.
- **Keyring/persistent cache:** deferred — v1 is in-memory only, per the issue.
- **`prepareArguments`-based interception:** a compatibility shim (pi docs), not a security boundary; not used for the guard.

Consequences: the security guarantee is real (bash→interactive-sudo never spawns), at the cost of a new single-purpose package and the guard applying to subagent children too (where `sudo_exec` itself is blocked headless). The scanner's strictness is the main ongoing risk — over-blocking would break legitimate `sudo -n`-style usage, so the allowed-flag set and quote/heredoc handling are part of the tested contract.
