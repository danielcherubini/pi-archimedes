# Treat a subagent's tool allowlist as a closed set, and report three run outcomes

pi 1.0.4 changed `--tools` so that it *keeps* MCP tools unless an entry starts with `mcp__` and added `--no-mcp`; 1.1.0 added `+name`/`-name` entries as **modifiers** to the list rather than as names; and 1.2.0 made print mode exit `1` with a stderr warning when the final response hit the output token limit. Our spawn path is `packages/subagent/src/spawn.ts:227-233`, which joins `agent.tools` verbatim into `--tools` and appends `--exclude-tools subagent`, with no validation on either side. We decided to pass `--no-mcp` unless an agent config opts in, to validate `tools:` entries at both edit time and spawn time, and to replace the binary pass/fail result with `completed` / `truncated` / `aborted`.

A `tools:` list in an agent config reads as a closed set — "this agent may use these three tools" — and after 1.0.4 it no longer is one: a child configured with `read, bash, edit` also receives every connected MCP server, plus `codemode` and `tool_search` when `defaultTools` enables them. We chose to restore the closed reading by default because the other surprises in this range were all of the widening kind, and ADR 0010 already established that this suite prefers a privilege that must be asked for over one that arrives by inheritance. The modifier change makes the same field actively dangerous rather than merely leaky: the `/agents` panel accepts a comma-separated list (`agent-panel.ts:469,1020`), so an entry like `+web_search` used to be a nonexistent tool name that did nothing and now silently alters the meaning of the entire list. Validating entries on edit as well as on spawn follows ADR 0008's model pre-validation precedent — reject the value with a specific message before it reaches a child process — rather than inventing a second input-validation pattern.

The exit-code change is a different failure: information destroyed rather than added. `packages/subagent/src/stream.ts:206-210` reduces the child to `code ?? 1`, so once 1.2.0 exits `1` for a response truncated at the output token limit, a genuinely useful-but-cut-off answer reports as the same generic failure as a crash. That particular loss cannot be reconstructed downstream — nothing else in the result says "the answer was cut off". So the run outcome becomes three-valued, derived from the child's own `stopReason` and 1.1.0's `agent_settled.aborted` (we currently conclude on `agent_end`, `stream.ts:197`, which fires for a cancelled run too), with cost accounting preserved in all three cases.

**Considered Options**

- **MCP opt-out** — pass `--no-mcp` only when a setting asks for it, preserving today's widened behaviour for users who want MCP tools in children. Rejected: it keeps the closed-set reading wrong by default, and the fix for a user who wants MCP in a child is one config line, whereas the fix for an unexpected MCP surface is noticing it first. Defensible if the widening turns out to be what people configured for; we have no evidence either way today.
- **Validate `tools:` only at spawn** — rejected: it leaves the `/agents` panel accepting malformed input that has to be reported later anyway, and the panel is where the mistake is typed. Pre-validation is cheaper to explain than a deferred error, and ADR 0008 already does exactly this for models.
- **Keep a binary outcome and encode truncation in the message text** — rejected: the model and the Archimedes Client both consume the subagent result, and a string that happens to say "truncated" is not something either can branch on. A named outcome is also what makes a future retry-on-truncation policy expressible.
- **Trust `--exclude-tools` for MCP instead of `--no-mcp`** — rejected: exclusion is a name-matching operation over a set we cannot enumerate (servers connect at runtime), while `--no-mcp` is the host's own statement of intent.

**Consequences**

- Agent configs that *want* MCP tools in a child need an explicit opt-in field, and existing configs silently lose MCP access on upgrade. That is the intended direction of the change, but it is a behaviour change and belongs in the release notes, not only in a changelog line.
- Malformed `tools:` entries — empty, duplicated, or `+`/`-` prefixed — are now rejected where they were previously accepted and ignored, so a config that carried one by accident is corrected at config read and in the `/agents` panel instead of quietly misbehaving. An entry that is well formed but names a tool not currently available is **not** rejected: it warns at dispatch and the dispatch proceeds, because a legitimate name disappears whenever its plugin is toggled off or its MCP server is disconnected, and failing there would make `tools: web_search` unusable for anyone who disabled `web`.
- The run outcome is now part of the tool-result contract the calling model reads, and of what the bridge reports to the Archimedes Client; both consumers must handle `truncated` and `aborted` rather than treating non-`completed` as an error string.
- Outcome derivation depends on the child's `stopReason` and `agent_settled.aborted`, which is one more reason subagent's floor is `>=1.2.0` (ADR 0026) rather than a documentation-only number.
- `--no-mcp` and the modifier syntax are pi 1.0.4/1.1.0 CLI surface. They are CLI, not typed API, and they reach the child as argv strings — `packages/subagent/src/spawn.ts` pushes `"--tools", agent.tools.join(",")` (`:229`) and `"--exclude-tools", "subagent"` (`:233`) — so a host change to what those strings *mean* leaves `tsc` with nothing to notice. The scheduled `pi@latest` job (ADR 0026) is consequently a compile-surface check and nothing more: it type-checks our exported types against whatever pi publishes today, runs no tests, and never spawns pi. It catches the typed half of drift only. The CLI-flag contract and the three run outcomes are guarded by the behavioural tests the pi 1.x alignment plan requires in Tasks 8 and 9 — the spawn-argv tests that a non-empty `tools:` list puts `--no-mcp` on the command line and that `mcp: true` removes it, the `stream.ts` tests that exit 1 with `stopReason: "length"` yields `truncated` and `agent_settled.aborted` yields `aborted`, and Task 8's tests for the event-shape and CLI-semantic drifts — not by the float job. Those tests are what go red when the host changes meaning under us; the float job is the early-warning tripwire for the part `tsc` can actually see.

**Verification note (live pi 1.2.0, 2026-10-13).** Implementation-time checks against an installed 1.2.0, several of which corrected assumptions this document was written with:

- **A child's declared tool list was already closed against MCP; `--no-mcp` closes the *registration*.** A non-empty `--tools` that names no `mcp__` entry keeps MCP tools *registered* — reachable through `codemode` and `tool_search` — but `_isActivatable` withholds their *declaration* to the model (`dist/core/agent-session.js`, `_allowlistFiltersMcp` → `_isAllowedTool` → `_isActivatable`). So "a child configured with `read, bash, edit` also **receives** every connected MCP server" is true of the tool box, not of the declared list, and `--no-mcp` is what stops the servers connecting at all. Two live dispatches with `tools: [read]` show the model with exactly one tool (`read`), with and without the flag.
- **Open follow-up: `mcp: true` is narrower than "gets MCP tools back".** With a non-empty allowlist the child's declared set is identical with and without the opt-in, so the field currently only decides whether the servers connect. Making an opting-in child actually able to call MCP tools needs the allowlist itself to match them (an `mcp__` entry flips `_allowlistFiltersMcp` and declares what it matches); a live attempt with `--tools read,mcp__*` declared none, and the probe runs that would have distinguished registration from declaration had no MCP server connected (`pi.getAllTools()` reported 0 MCP tools in all three variants, including the unfiltered baseline), so the mechanism is unresolved and needs its own investigation rather than a guess here.
- **A cancellation arrives as exit code 143 (or 129), not as a signal.** print mode catches SIGTERM, and SIGHUP off Windows, and calls `process.exit(signal === "SIGHUP" ? 129 : 143)` (`dist/modes/print-mode.js`, `registerSignalHandlers`), so `close` reports a code and no signal and no `agent_settled` frame. Reading only the signal classified every cancelled dispatch as a failure.
- **`--mode json` never maps `stopReason` onto the exit code at all.** The whole mapping, including 1.2.0's truncation exit, sits inside print mode's `if (mode === "text")` branch — so a json child whose last response ended `stopReason: "error"` exits 0 with clean stderr. A failed run therefore has to carry its own explanation, and `isError` keys off that explanation rather than the code.
- **A `tools:` written as a YAML list parsed to an array and was silently dropped**, leaving the child with no allowlist at all — found by dispatching a real config that said `tools: [read]` and getting a child listing 216 MCP tools. The read path now accepts all three spellings pi's parser produces and rejects anything that is not a list of names.
