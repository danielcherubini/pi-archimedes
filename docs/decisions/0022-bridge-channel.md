# Bridge channel: env-gated local channel from the suite to the Client

The Archimedes Desktop (the **Client**) manages agent processes and runs the archimedes suite in RPC mode, where `ctx.hasUI` is `true` but no TUI surface exists — so interactive tools (`ask`, `sudo_exec`) are broken and ambient state (todos, cost, subagent streams) is invisible. We decided to give the suite a local channel to the Client, generalizing the existing subagent socket pattern: the suite talks out-of-band to its manager — the main pi process in subagent mode, the Client when the Client manages the process.

We decided (2026-08, design discussion) on:

- **Env-gated activation, herdr semantics.** The bridge is active only when the Client set `PI_ARCHIMEDES_BRIDGE=1` + `PI_ARCHIMEDES_BRIDGE_SOCKET` + `PI_ARCHIMEDES_BRIDGE_SESSION` + `PI_ARCHIMEDES_BRIDGE_SERVER_PID` (the desktop's own pid, for the agent's `GetNamedPipeServerProcessId` check) at spawn. Inert otherwise — a plain terminal run never sees it. The Client is the only actor; there is no user-facing settings namespace and no plugin-manifest entry. `PI_ARCHIMEDES_BRIDGE_SESSION` carries the **desktop's own session id** (created before spawn) — NOT the ACP `sessionId`, which is agent-generated in the `session/new` response and does not exist at spawn time. The `session` push frame carries the *pi* session refs (`ctx.sessionManager`), letting the desktop map desktop-session ↔ ACP-session ↔ pi-session.
- **A module in `core` (`core/src/bridge/`), not a new package.** Core is every package's peer dependency, so the bridge ships with any archimedes package (including standalone installs) and the ask/sudo delegates import it exactly like they import the bus. A new package would need full AGENTS.md release wiring and a new dependency edge for no user-facing benefit.
- **The root-only gate.** The bridge is active only when `PI_SUBAGENT_SOCKET` is **absent**. Subagent children inherit the Client's env (fork passes `...process.env`), and their `ctx.mode` is not `tui`, so env presence alone would make a child claim bridge mode; the child's manager is the parent, not the Client. The Client-managed root has the bridge vars and no subagent socket → active.
- **TUI mode always wins.** At the first `session_start` the bridge captures `ctx`; `ctx.mode === "tui"` → permanently inactive, even if env vars are present. The mode is a process-level property, so one evaluation suffices.
- **Channel mechanics (herdr + subagent precedents).** The Client is the server (0600 Unix socket under a 0700 dir; named pipe on Windows). Ephemeral connections: one `net.createConnection` per message; interactive requests keep the connection open until the reply frame. Line-delimited JSON frames, all carrying `v: 1`: push `{v,type:"push",seq,event,payload}` (seq = per-process monotonic, herdr-style, **starts at 1**; the Client drops `seq <= lastSeq` — covers reordering AND duplicate delivery; **`lastSeq` is scoped per bridge listener / per spawn** — a respawn resets it by construction; all push payloads are absolute-state and idempotent), request `{v,type:"request",id,method,source,toolCallId,params}` (id = UUID; source = `"main"` (root) or `"subagent:<name>"` (relayed child); toolCallId = the tool-call id of the invoking process — for a root ask the same id pi-acp emits in `tool_call` frames, for a subagent ask the child's own id which pi-acp never frames, so the Client anchors by `source`; **`toolCallId` is nullable/absent for `confirm`/`password`** (invoked from `prompt.ts`'s choke point with no tool-call id in scope; `source` is `"main"` for them, since sudo is root-only); `params` = the method's params, no duplicated `toolCallId`), response `{v,type:"response",id,result|error}`. Pushes: ack line, initial attempt + 2 retries (500→1500 ms) then drop, coalesced to at most one in-flight connection per event type (latest payload wins). Interactive: 5-min timeout → cancel; **connection close = immediate cancel on both ends**; the Client sends an explicit terminal frame (`error:"cancelled"`) before closing on timeout/drain/auth-failure; the Client's waiter cap is 330 s (agent timeout + 30 s margin, so the agent's cancel deterministically wins); unreachable channel → fail fast. **Refcount invariant: every `ASK_REQUEST` is eventually paired with an `ASK_RESPONSE`** (success, error, timeout, cancel, child exit, session close) so the `state` refcount never leaks; a child exit cancels the relayed Client request immediately (the bridge's own 5-min timeout is the backstop for a child that neither answers nor exits). **Child-exit wiring:** `spawn.ts` gains a socket-close/child-exit handler that emits a new `ASK_CANCEL` bus event (requestId + source); the bridge subscribes, cancels its Client request, and emits the **single** pairing `ASK_RESPONSE` — the bridge is the **sole emitter** of child-path `ASK_RESPONSE` (`spawn.ts` signals, it does not emit — no double-decrement). **Root-path emitter:** the root path's `ASK_RESPONSE (main)` is a **new emission added to the tool's bridge branch**, emitted exactly once when `bridge.ask` settles (success, error, or timeout) — the tool's `ASK_REQUEST (main)` emission is unchanged (a notify hook), and the existing TUI path never paired it, so this is new code, not a mirror. **Peer verification**: the Client accepts a connection only if the connecting process is **a descendant of the desktop itself** — the anchor is the desktop's own pid (`std::process::id()`, always alive, so no liveness check is needed), NOT the spawned agent's pid (the ACP SDK spawns the agent internally and does not expose the child pid). The topology is desktop (D) → `pi-acp` (A, a direct child of D) → `pi` (P, a grandchild); the peer connecting to the desktop's socket is `pi` (P). The desktop reads the peer's pid (`SO_PEERCRED` on Linux, `GetNamedPipeClientProcessId` on Windows) and walks the parent chain up to the desktop's own pid (Linux `/proc/<pid>/status` `PPid`, bounded ≤8 hops; Windows Toolhelp snapshot) — if the chain doesn't reach the desktop's pid, **reject the connection** (fail-closed). The spawned child's exit tears the listener down + unlinks immediately (closes the pid-reuse window; Windows: the pipe instance vanishes when the last handle closes — no unlink API). **Agent→Client (Windows, v1 limitation):** the agent-side `GetNamedPipeServerProcessId` check is a **documented v1 limitation** (Node's `net` exposes no such API — it would need a native addon); in v1 the agent presence-checks `PI_ARCHIMEDES_BRIDGE_SERVER_PID` only, and the desktop-side descendant check is the real defense. The Client creates the **first** pipe instance with `FILE_FLAG_FIRST_PIPE_INSTANCE` (pre-squat detection) and subsequent listener instances **without** it (so its own concurrent connections work). The match trusts the desktop's entire process tree (the `pi-acp` direct child, the `pi` grandchild, and any command the agent executes); the trust boundary is the desktop's process tree, slightly wider than the agent's (it also covers the desktop's other children), but the desktop only spawns the agent, so the practical widening is nil *(amended — see the terminal-children note under Consequences)*; responses ride the originating verified connection. The suite's `active` flag does not depend on a successful connection: the suite connects lazily per message; a failed connect is a no-op for pushes and a fail-fast error for interactive requests.
- **Bus payload types are the wire types.** `ask` replies use the existing `AskResponsePayload`; pushes use `TodoUpdatePayload`/`TodoClearPayload`/`CostUpdatePayload` verbatim — including the **subagent todo path, which already exists**: parent-side `subagent/src/stream.ts` watches the child's `manage_todo_list` executions and emits `TODOS_UPDATE`/`TODOS_CLEAR` on the parent bus with a unique `source` per child (cleared on child exit), so the bridge's bus subscription receives subagent columns for free. `state` (`working`/`idle`/`blocked`, herdr's refcounted state machine: +1 on `ASK_REQUEST` any source, −1 on `ASK_RESPONSE`; **the machine: `refcount > 0` → `blocked`; `settled ∧ refcount == 0` → `idle`; else `working`** — so `agent_start` → `working` only when `refcount == 0`, and a pending ask keeps `blocked` through `agent_settled`) and `session` (`ctx.sessionManager` refs, herdr's `report_agent_session`, **re-emitted on every `session_start`** so a lost frame is recoverable, and the payload **echoes `PI_ARCHIMEDES_BRIDGE_SESSION`** so the Client can assert the connection↔session mapping) are the only new shapes. No new payload vocabulary.
- **Socket lifecycle.** Per-spawn randomized socket path under the 0700 dir; the Client starts the listener before the spawn call returns (the push retry window is only ~2 s); unlink on session close; tolerate/clean stale files at startup; two concurrent sessions never share a socket. **Forward compatibility:** the Client ignores unknown push events (still acks) and answers unknown methods with an `error` response.
- **Ask data flow (one path, no double-handling).** Root asks in bridge mode: the tool's new branch calls `bridge.ask(params, toolCallId)` directly (passing the tool's `_toolCallId` argument; the bridge puts it in the frame, not in `params`); the tool's bus `ASK_REQUEST` emission (source `main`) is unchanged (notify + the bridge's `blocked` state refcount). Child asks: child socket → parent `spawn.ts` → bus `ASK_REQUEST` (source `subagent:<name>`) → the bridge consumes it in bridge mode (exactly as `ipc-relay` does in TUI mode — including skipping `source === "main"`), forwards to the Client, and emits `ASK_RESPONSE` on the bus so `spawn.ts` writes it to the child. **The `ask_request` socket payload and the bus `ASK_REQUEST` payload are extended to carry the tool-call id** (from the tool's `_toolCallId` argument); `spawn.ts` propagates it, and the bridge uses it for the request frame's `toolCallId` (and sets `source`). **Child exit:** `spawn.ts`'s socket-close/child-exit handler emits a new `ASK_CANCEL` bus event (requestId + source); the bridge subscribes and cancels the Client request (see the channel-mechanics bullet). **The `ipc-relay` is gated on `!getBridge().active`** (in addition to skipping `source === "main"` and requiring `ctx.ui`) — the gate is checked **per-message in the subscription handler, not at registration** (`registerIpcRelay` runs at extension load when `bridge.active` is false in every mode; the mode is only captured at the first `session_start`, so a registration-time gate would silently reintroduce the double-consumption bug). Gating on `!getBridge().active` (rather than `ctx.mode === "tui"`) preserves today's behavior in **both** TUI and RPC-no-env (relay on) and diverts only in bridge mode (relay off, bridge on) → exactly one consumer per source. The response→results helper serves all three sources (subagent socket, TUI picker, bridge).

Considered and rejected:

- **ACP-only enrichment:** ACP carries `raw_input`/`raw_output` (read-only rich cards are possible) but has no agent→client input channel — `session/request_permission` is approve/deny only. Interactive tools cannot work without a side channel.
- **A standalone managed extension file (herdr contract) re-registering the tools:** pi's tool-override semantics (last-registered wins) allow it, but it would duplicate `sudo_exec`'s execute (process-group kill, credential cache, fail-streak, ticket probe) outside the package's tests and depend on extension load order to beat the package's tools. See 0021.
- **A long-lived persistent connection:** more connection-state to manage (reconnect, half-open detection) for no benefit — the subagent socket precedent already proves the ephemeral pattern at 5-minute request lifetimes.

Consequences: the suite gains a second, local, same-user surface for user input and state; its trust boundary is the spawn-env handshake, not a network boundary. The `PI_SUBAGENT_SOCKET`-absent gate is not self-evident from the code — it exists because fork inherits env; keep the comment. Subagent children remain non-promptable (see 0021).

**Terminal children inherit the bridge env (v1 edge case).** A shell spawned by the desktop inherits all four `PI_ARCHIMEDES_BRIDGE_*` vars; a `pi --mode json` run inside such a shell satisfies the activation gate (env present + non-TUI + no `PI_SUBAGENT_SOCKET`) and activates the bridge. This is not a security hole (same user, same spawn-env trust boundary), but it contradicts the "the desktop only spawns the agent" assumption — the bridge can be activated by non-agent descendants. Desktop-side mitigation: strip the four `PI_ARCHIMEDES_BRIDGE_*` vars from non-agent children's environments (only the agent spawn carries them).
