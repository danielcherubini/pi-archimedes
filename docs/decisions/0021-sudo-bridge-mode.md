# Sudo in bridge mode: Client-supplied confirm + password (amends 0010)

0010 blocks `sudo_exec` in headless sessions (`ctx.hasUI === false`) and defers "child `sudo_exec` via IPC socket bridge". The Archimedes Desktop (the **Client**) now manages agent processes directly and runs the archimedes suite in RPC mode, where `ctx.hasUI` is `true` but no TUI surface exists — so `sudo_exec` is broken there for the same reason. The **bridge** (Decision: the suite's env-gated local channel to the Client, see the glossary) makes the Client-managed root process promptable again without weakening 0010's security posture.

We decided (2026-08, design discussion) on:

- **Bridge mode is a promptable session.** A session is promptable when the bridge is active: bridge env vars present at spawn, `ctx.mode !== "tui"`, and `PI_SUBAGENT_SOCKET` absent (the process is the Client-managed root, not a subagent child). In bridge mode the confirm gate is the Client's `confirm` modal — which displays the exact command + human-readable reason and requires explicit consent — and the password gate is the Client's masked modal (the bridge `password` method). Headless sessions without a bridge remain blocked with a clear error; subagent children remain blocked (their `ask` relays via the parent, which is promptable in its own mode). **The bridge routing lives in `prompt.ts` (the single choke point), and the headless gate is unchanged**: `confirmCommand` and `promptForPassword` each prepend `if (bridge.active) return bridge.confirm/password(...)`; the existing `ctx.mode !== "tui"` headless gate in `promptForPassword` sits after the bridge branch, **unchanged** (0010's guarantee preserved verbatim). The tool calls `confirmCommand`/`promptForPassword` unconditionally — `prompt.ts` is the single place where the bridge routing and the headless gate both live, so every caller (current and future) stays safe.
- **0010's guarantees are preserved verbatim.** The password only ever flows Client masked UI → bridge channel → `sudo -S` stdin — never argv, env, logs, files, or a tool parameter. The single in-memory credential cache is unchanged: a bridge-supplied password is cached the same way and cleared under the same conditions (auth failure, TTL, `/sudo forget`, `session_shutdown`). The bash→interactive-sudo `tool_call` veto is untouched (mode-independent).
- **The channel is the trust boundary — verified by process identity, not just file mode.** The bridge channel is a 0600 Unix socket (named pipe on Windows) under a 0700 directory, local to the same user, set by the Client at spawn. A 0600 file is a *user* boundary; a same-user process can read the agent's environ and connect. So the Client additionally verifies the connecting process is **the spawned pid itself or a living descendant** of the agent process it spawned (the Client spawns `pi-acp`, which spawns `pi --mode rpc`; the bridge runs inside `pi`): it records the spawned pid, reads the peer's pid (`SO_PEERCRED` on Linux, `GetNamedPipeClientProcessId` on Windows), walks the parent chain to the spawned pid, and checks the **anchor pid's** liveness via the retained spawn handle (kept for the session lifetime; intermediates covered by the live-chain walk — a dead intermediate reparents the peer, breaking the chain; fail-closed when the chain is dead/broken or the check is unavailable). **The match trusts the entire spawned process tree** — including any command the agent executes (bash children, MCP servers, subagents) — so the guarantee is only against non-agent same-user processes; a direct `password` call from such a process skips the confirm gate, which is why the `SudoPasswordModal` displays `command` + `reason` verbatim. The agent additionally verifies the server it connects to is the real Client (`GetNamedPipeServerProcessId` vs `PI_ARCHIMEDES_BRIDGE_SERVER_PID` on Windows — the defense against a second-instance squat); the Client creates the first pipe instance with `FILE_FLAG_FIRST_PIPE_INSTANCE` (pre-squat detection) and subsequent instances without it. The password appears in the reply frame only, is written to `sudo -S` stdin, and the **bridge-channel copy is dropped** (the pre-existing in-memory credential cache retention is unchanged — 0010's scope); it is never logged, cached in the frame, or written to disk. The desktop's ACP `session/request_permission` prompt is a separate, upstream gate (approve/deny the tool call) and does not replace the confirm gate.

Considered and rejected:

- **Stay blocked in bridge mode (status quo):** keeps 0010 untouched, but `sudo_exec` is unusable in the desktop — the exact gap this decision closes.
- **Standalone managed extension file overriding the tool (herdr contract):** pi's tool-override semantics (last-registered wins) allow a managed file to re-register `sudo_exec`, but it would duplicate the tool's execute (process-group kill, credential cache, fail-streak, ticket probe) outside the package's tests, and depend on extension load order to beat the package's tool. The two-ternary delegate inside the package keeps a single source of truth.
- **A `password` tool parameter:** the original 0010 rejection — the LLM context and the ACP wire would carry the credential. The bridge keeps the credential out of both.

Consequences: the bridge channel (a new `core` module) is a second, local, same-user surface for credentials; its permission model is the spawn-env handshake plus a two-direction process-identity check (Client→agent descendant match; agent→Client `GetNamedPipeServerProcessId` on Windows), not a network boundary — and the descendant match trusts the whole spawned process tree (agent-executed commands included). The 0010 "headless blocked" clause is **unchanged** (`ctx.mode !== "tui"` → reject) — the bridge routing is a separate branch before it. The deferred "child sudo_exec via IPC socket bridge" is scoped: the Client-managed root is in scope; subagent children remain out.
